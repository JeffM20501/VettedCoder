FIXED DESIGN DECISIONS (the spec)

IDs and identifiers
- All primary keys are UUIDv7, generated in the application with Python's uuid.uuid7(). Sessions expose public_id like "vetted-x92k1a" (random, at least 6 alphanumeric chars after the prefix). Organizations use slug. Sessions and organizations are addressed by public_id or slug in URLs, never by UUID.
- Authorization never relies on ID secrecy. Cross-tenant access returns 404 (not 403) so existence never leaks.

Cross-cutting API rules
- Base path /api/v1. Error envelope on every non-2xx: {"error": {"code", "message", "details", "request_id"}}. Cursor pagination on every list endpoint (default 25, max 100, clamped). Never leak SQL, stack traces, or internal exception text.
- Soft delete on core entities (deleted_at); deleted rows are invisible through the default manager and the API; unique constraints apply only to non-deleted rows.

Database schema (tables, key columns, and constraints that Module 2 tests must prove with direct DB writes)

Authentication and accounts
- Argon2id hashing in production settings; minimum password length 12 plus Django validators.
- JWT in cookies (Secure, HttpOnly, SameSite=Lax); access token 15 minutes; refresh token 7 days with rotation. Unsafe methods under cookie auth require a CSRF token.
- Login blocked until email is verified. Register and password-reset return identical responses whether or not the email exists (no enumeration).
- Refresh rotation: using a refresh token revokes it and issues a new one in the same family. Reusing an already-used token revokes the whole family.
- Email verification token: single use, 24h. Password reset token: single use, 1h; a successful reset revokes all of that user's refresh tokens.
- Rate limits: login 5/min per IP+email; register 5/hour per IP; password reset 3/hour per email; guest token redeem 10/min per IP.

Guest access and candidate tokens
- Token: 256-bit CSPRNG, URL form /interview/vetted-<token>. Only the SHA-256 hash is stored. The plaintext never appears in the DB, logs, error messages, audit rows, or API responses after creation.
- expires_at = scheduled_end_at + 2 hours (unscheduled sessions: created_at + 24 hours). Valid at expires_at minus 1 microsecond, invalid at expires_at.
- Revoked, expired, unknown, or wrong-session tokens return the SAME error (code "invalid_token", same status and body shape).
- Regenerate = revoke previous + create new, atomically. Redeeming issues a guest cookie scoped to that participant and session only. A guest may join from 15 minutes before scheduled_start_at.
- Guest linking: runs only when a user VERIFIES an email matching (case-insensitively) a guest_profile email. Unverified registration never links. Linking is transactional and idempotent, rewrites that guest's participant rows to the user, sets linked_user_id and linked_at, and writes an audit row.

Organizations
- Roles per membership: owner, admin, interviewer, member; a user can hold different roles in different organizations. MVP rule (service layer, behind a setting, NOT in the schema): a user belongs to at most one organization.
- Always at least one owner: the last owner cannot leave or be demoted (also under concurrency).
- Invitations: hashed token, single use, 7-day expiry, revocable, acceptable only by an authenticated user with a VERIFIED email matching the invitation.
- Permissions: owner (everything incl. deleting the org), admin (members, questions, templates, retention, all org sessions and playback), interviewer (create sessions, questions, scorecards), member (read org questions, practice sessions).

Questions
- Content is immutable and versioned. Editing creates a new QuestionVersion and moves current_version. Sessions pin question_version at assignment, so later edits never change past sessions.
- test_cases shape: {"schema_version": 1, "public": [{"id", "input", "expected_output", "timeout_ms"}], "hidden": [...]}; invalid shapes are rejected with field-level errors.
- Visibility: global, organization (org members only), private (creator only). Questions belong to the organization; they remain when the creator leaves or is soft-deleted.
- Hidden test cases and reference solutions NEVER appear in any response seen by a candidate, observer, or member (assert recursively over the whole body). Interviewers see hidden results only as pass/fail with test id; only owners/admins of the question's organization (or its creator) see inputs and expected outputs.

Sessions
- Allowed transitions only: scheduled->waiting (first participant joins), waiting->active (interviewer starts), active->completed (interviewer ends), completed->archived (only when the playback artifact is ready), scheduled|waiting->cancelled, scheduled|waiting->expired (past scheduled_end_at + 2h with no start; Celery beat job). Every other transition is rejected with code "invalid_transition". Test every (from, to) pair.
- Interview-type sessions need at least one interviewer and at least one candidate before start. Capabilities: interviewer and co_interviewer (edit code and whiteboard, run code, chat, private notes, scorecards, start/end); candidate (edit code and whiteboard, run code, chat); observer (read-only code and whiteboard, private notes, no chat, no run, no scorecard).

Evaluation
- Notes are private to the author; not even org admins can read them. One scorecard per author per session; editable while draft, locked after submit. Ratings must be within the criterion's scale; evidence offsets within the session duration.
- Blind review: another interviewer's submitted scorecard is visible only after you have submitted your own; admins and owners see all.
- Candidates see feedback only if candidate_feedback_visible is true AND a scorecard is submitted, and then only summary text and per-criterion comments, never the recommendation or notes.

Real-time
- Yjs over a Node y-websocket sidecar. Django issues a room ticket (JWT, 60 s expiry, bound to session, participant, and role). The sidecar reports events to Django through an internal endpoint authenticated with a shared secret. Cursors and selections use Yjs awareness. Firebase RTDB is only for room signaling and Excalidraw; Django mints Firebase custom tokens scoped to the session path and the participant's edit rights.
- Read-only roles' writes are dropped and counted; writes to a non-active session are rejected; presence updates faster than 50 ms per connection are dropped.

Code execution
- python 3.11+, javascript (Node 20+), typescript (esbuild, in-memory). Limits: 5 s CPU, 10 s wall, 512 MB RAM, read-only root FS, no network, no package installs, source at most 100 KB per file, output capped at 64 KB (truncated flag). Run rate limit: 1 per 2 s per participant, burst 3.
- Verdicts: passed, failed, compile_error, runtime_error, time_limit_exceeded, memory_limit_exceeded, runner_unavailable.

Event pipeline and playback
- Server-side writer only; clients never write to DynamoDB. Per-session sequence numbers strictly increasing and gapless; duplicate event_id is idempotent.
- vc_session_events: PK session_id, SK seq (N). Sparse GSI by_type (PK session_id, SK type_key) only for code_run, test_result, chat_message, whiteboard_snapshot, question_changed, file_open, participant_joined, participant_left, session_started, session_ended. expires_at = write time + 30 days. No scans anywhere. Edits are stored as Yjs binary updates.
- vc_session_checkpoints: PK session_id, SK elapsed_ms (N), written every 60 s or 100 edit operations, stores last included seq.
- Flush batches of up to 25 items or 500 ms. Seek(T) = latest checkpoint with elapsed_ms <= T, then events with seq > checkpoint.seq.
- Archive (Celery, on completion): manifest.json plus chunks/{n}.json.gz under sessions/{session_id}/playback/{yyyy}/{mm}/{dd}/{bundle_id}/, each chunk starting from a checkpoint; verify SHA-256 before marking the artifact ready; idempotent; retried on failure; session becomes archived only after ready. Playback after TTL is served from S3. Pre-signed URLs expire within 5 minutes and are issued only after an authorization check.
